# Fix Prompt (Round 3): Make the Reports Match the Data, Finish Registry Ingestion, Enforce the License Gate

## Context
Round 2 fixed several real problems (MPL-2.0 reverted, more honest capability labels, Stripe pairing fixed, vendor seeds found). An independent review of the new `RESULT-REPORT.md` still found contradictions between what the report claims and what the data can support. This is the **last planned fix round**, so be rigorous: for every claim, run the query or file check, and put the evidence in the report.

Work in the existing project. Do not rebuild what works (watcher, map layer, safety gates, tests).

## Ground Rules
1. **Every table and number in every report is generated by a script from `registry.db` and the filesystem.** No hand-written tables. If a script cannot produce a value, the report says `not determined`.
2. **If the report and the data disagree, the data wins and the report says what was wrong.**
3. **Never mark something fixed unless a test or check proves it.** For each item below, add the verification command and its output to the report.
4. **Unknown license, unknown capability, or unknown secrets means not eligible for `selected`.**
5. No server code is installed or executed. No secrets stored. The agent never approves a server. Do not change `approvals` content.
6. Do not decide license policy for the user. Keep `allowed_licenses` exactly as the user set it (currently `[MIT, Apache-2.0, BSD-3-Clause, CC-BY-4.0]`).

## Item 1: MCP registry ingestion was incomplete
The registry reports 58,646 records over 587 pages (about 100 per page). Only 1,034 servers were ingested, which is roughly 10 pages. The report never says how many pages were fetched or whether pagination finished, and it calls the result "62,000+ cataloged records".

### Fix
1. Inspect `cursor_state.json` and the sync code. Determine why ingestion stopped (a page cap, a time limit, a rate limit, or a bug).
2. Finish ingestion: paginate to the end of the registry using the cursor until the API returns no next cursor. Respect rate limits with back-off, persist the cursor after every page, and resume safely if interrupted.
3. Record in a new table `mcp_sync_runs` (and in the report): run start and end time, total pages fetched, total records fetched, unique server names, unique names with `version=latest`, records skipped as invalid (with reasons), final cursor value, and **whether pagination completed (true/false)**. If it did not complete, the report must say so and must not use the words "full" or "complete".
4. Explain the 58,646 vs. unique-server gap with data (how many records are older versions of the same server).
5. Remove the phrase "62,000+ cataloged records" and any similar total that is not the number actually stored in the database.
6. Re-run the funnel (developer-tool fit, license, vetting floor, relevance) over all ingested candidates and print the counts at every stage.
7. Re-run the seed lookups. For AWS, list every `io.github.awslabs/*` and Amazon-namespaced server found, not just OSCAL.

## Item 2: The license gate was not enforced on MCP servers
18 of the 26 selected servers show license `None`, yet the funnel claims every selected server passed an allowed-license check.

### Fix
1. For every MCP server, resolve the license in this order: the registry record's license field (if present), the repository's `LICENSE` file or GitHub license metadata, the package manifest (`package.json`, `pyproject.toml`). Store the result and the source used (`license_source`).
2. Apply the gate: a server whose license is not in `allowed_licenses` (including `None`/unknown) **cannot be `selected`**. Servers that fail become `candidate` with the reason `license: unknown` or `license: <value> not allowed`.
3. Re-run selection. Print every server that was `selected` before and is now dropped, with the rule that failed.
4. Add a test that fails if any `selected` server has a license outside `allowed_licenses`, and include it in `verify_vault.py`.
5. List in `DECISIONS-NEEDED.md` the servers dropped only because of an unknown license (so the user can check upstream) and the ones dropped for a disallowed license (MPL-2.0 Terraform server, and any others).

## Item 4: The pinned-slot table inflates coverage
Problems found:
- 23 slots are labeled "renamed / alternate", but most are positional replacements, not renames (for example pinned `insecure-defaults` became `semgrep-rule-creator`; pinned `ansible` became `aws-serverless`).
- Six skills fill two slots each: `codeql`, `stride-analysis-patterns`, `firebase-security-rules-auditor`, `observability-engineer`, `terraform-skill`, `security-audit`.
- Trail of Bits pinned slots (50-58) are not filled by Trail of Bits skills. They should read unfilled (license decision pending), not "renamed".
- Pinned slots 11, 12, 15, 25-29 are unfilled but are silently backfilled by unlisted skills.

### Fix
1. **Strict matching only.** A slot is `matched` only if the selected slug equals the pinned slug (or an explicitly documented alias in `catalog.yaml` `aliases:` that the user can see). Otherwise the slot is `unfilled`.
2. **A skill occupies at most one pinned slot.** Remove double assignments.
3. **Separate unpinned selections from pinned slots.** Skills selected as backfill are reported as `backfill (unpinned)` in a separate table, with the module and the reason each was chosen (relevance score, source). They count toward the module total but are never presented as matching a pinned slot.
4. Report two numbers per module and overall: `pinned slots matched / pinned slots in module` and `total selected / target`.
5. Generate the reconciliation table from the database. Statuses allowed: `matched`, `alias (documented)`, `unfilled (reason)`. For unfilled slots, give the real reason from the log, for example `repo not synced`, `skill not found in repo`, `license not allowed`, `failed validation`.
6. If the 99-selected figure is kept, explain how it is composed: pinned matched + backfill.
